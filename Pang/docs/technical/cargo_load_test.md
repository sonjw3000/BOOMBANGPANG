# Cargo Load Test

`Tools > Universe Logistics > Cargo Load Test`에서 실행하는 **Editor Play Mode 전용** 부하 테스트다.
저장된 GameScene을 실행한 뒤 사용한다. 생성물은 현재 Play 세션에만 존재하며, Play 종료 후 다시 실행하면 초기화된다.
임시 Footprint를 사용하므로 테스트 상태를 게임 저장 파일로 저장하거나 불러오지 않는다.

## 사용 순서

1. GameScene을 Play하고 초기화 완료를 기다린다.
2. 에디터 메뉴에서 Cargo Load Test를 연다.
3. 건물 쌍 개수 `n`, 작업자 수 `m`, 크기, 간격, Seed와 배치 영역을 지정한다.
4. `배치 검사만 실행`으로 공간과 외부 포트 접근성을 확인한다.
5. `테스트 환경 생성`을 누른다. 소스/목적지 포트 수와 실제 생성 작업자 수를 확인한다.
6. 게임 일시정지를 해제하고 `캡슐 공급 및 측정 시작`을 누른다.
7. 워밍업 후 지정한 실제 시간 동안 측정한다. 시간이 끝나면 신규 공급만 중단하고 기존 운반은 계속한다.
8. `CSV 저장`으로 결과를 저장한다. 다시 생성하려면 Play를 종료한다.

기본 맵은 현재 `GridService.BuildDefaultMap()`의 100×100이다. 이 도구는 기존 맵을 초기화하거나 확장하지 않는다.
요청한 개수가 들어가지 않으면 실제 생성 전에 실패한다. 개수·크기를 줄이거나 배치 영역을 조정한다.
생성 도중 설치/스폰 오류가 발생하면 일부 생성물이 남을 수 있으므로 Play를 종료하고 다시 준비한다.

## 생성 구조

- 1쌍은 중앙에 빈 공간이 있는 `+` Building 2개다. 둘 다 실제 Building으로 등록한다.
- 한쪽은 외곽 OB 포트, 다른 쪽은 외곽 IB 포트만 배치한다. 중앙 빈 공간과 중앙 쪽 벽에는 포트를 배치하지 않는다.
- 모서리처럼 실내·실외 상호작용 칸이 확보되지 않는 위치에는 포트를 설치하지 않는다.
- 각 쌍에 OB Building → IB Building 단방향 연결을 만든다.
- 전체 Bounding Box 사이에도 간격을 두는 보수적 배치다. 배치 영역 좌측 하단은 작업자 스폰 구역으로 예약한다.
- 생성 전 도면과 실제 설치 결과 모두 스폰 구역에서 모든 외부 포트 지점까지 4방향 통행 연결을 검사한다.
- 이동 검사에서 통행 가능한 Interaction 칸의 시설 참조를 장애물로 취급하지 않는다.
- 작업자는 전용 Spawn Area에 생성한 인간이며, 실외 소속(0), CargoTransfer 작업만 배정한다.
- 작업자의 기본 이동/작업 속도 배율은 1이다. 기본 활성화된 `테스트 작업자 피로 회복`은 생성한 인간에게만 1초마다 기존 TickRecovery를 호출한다. 기존 회복 API에 따라 위험 노출도도 감소한다. 옵션을 끄면 피로 누적과 휴식 요구도 원래 규칙대로 적용한다. 산소·사고 판정 로직은 변경하지 않는다.
- 설치 비용이 부족하면 EconomyService의 DebugAdjustment 거래로 필요한 전체 생성 비용을 지급한다.

건물 형태와 포트 방향은 현재 1×3 포트 Footprint를 전제로 한다. 정의가 바뀌면 생성 전에 거절한다.
무작위 배치는 `System.Random(seed)`를 사용하고, 스폰에 사용하는 Unity Random 상태는 생성 뒤 복원한다.
동일 초기 월드와 설정에서 배치 위치는 재현되지만 전체 시뮬레이션의 결정론을 보장하지 않는다.

## 실제 운반 경로

```text
BoxManager.GetNewBox(Capsule)
→ 선택 아이템 1개 추가, OB 물류 상태 설정
→ OutboundCargoPort.TryDockCapsule
→ 기존 도킹 이벤트 / OutboundWorkflowService
→ CapsuleRelocateCoordinator의 목적지 매칭·예약
→ TaskManager가 CargoTransfer 유형의 CapsuleRelocationTask 배정
→ 실제 작업자의 Pick / 이동 / Put
→ IB 도킹 이벤트
→ 이후 프레임에서 운반 예약 해제 확인
→ IB.TryUndockCapsule / BoxManager.DisableBox
```

테스트 스크립트는 Task를 직접 만들거나 완료시키지 않는다. 이벤트 콜백에서는 큐 등록과 카운트만 한다.
실제 공급·회수는 프레임당 상한을 적용한다. 소스당 캡슐 1개가 도착·회수된 뒤 다음 캡슐을 공급한다. 공급 간격은 회수 이후 실제 시간 기준이며, 과부하 시 상한 때문에 공급이 늦어질 수 있다.
따라서 `m`이 전체 OB 소스 수보다 크면 일부 작업자는 대기한다. 활동 작업자 부하를 늘리려면 `n`과 실제 OB 소스 수도 함께 늘려야 한다.
`공급 중지`는 기존 Task를 취소하지 않는다. 교착·피로 등으로 기존 운반이 남으면 회수 완료도 지연된다.

## 측정 해석

CSV는 워밍업 이후 약 1초마다 다음 정보를 저장한다.

- 전체 작업자 / 운용 가능 / Task 배정 인원 / 교통 차단 / 회복 필요 인원
- 실제 갱신 빈도, 프레임 시간 P95
- Unity `Main Thread` 마커 평균: 대기 및 Editor 비용을 포함하며 시뮬레이션 전용 CPU 시간은 아니다. 사용 불가 시 NaN.
- 테스트 도구의 프레임당 공급·회수 실행 시간
- 프레임별 GC 할당량의 구간 합계
- 공급 / OB Pick / IB 도착 / 회수 이벤트 개수와 구간 실제 시간
- 남아 있는 캡슐, 공급 큐, 회수 큐 크기

IB 도착은 실제 Put 성공 횟수이며 Task 완료 카운터와는 구분한다.
도구 자체의 Profiler 구간은 `CargoLoadTest.FeedAndCollect`, `CargoLoadTest.Sample`이다.
기존 시뮬레이션의 실행 비용은 Unity Profiler의 WorkerManager, TaskManager, 경로 탐색, 이벤트 처리 경로에서 확인한다.
렌더링·Scene View Gizmo·다른 창의 상태와 배속을 고정해 비교한다. 최종 인원 한계는 별도 Player 검증이 필요하다.

## 검증

`CargoLoadTestLayoutEditModeTests`는 동일 Seed의 위치 재현, 중앙 비소유 영역 보존, 계획 단계의 무변경,
접근 불가 거부, 공간 부족 시 사전 실패를 검사한다. 실제 운반은 Play Mode에서 별도로 검증한다.

2026-09-04 검증 결과:

- Unity 6000.5.3f1 컴파일 성공, 위 EditMode 테스트 3개 통과.
- Play Mode에서 `n=2`, `m=8`, 크기 11 / 팔 7 / 중앙 빈 공간 1 / 간격 4, Seed 12345,
  배치 영역 `(2, 2, 50, 50)`: 건물 4개, OB 56개 / IB 56개 생성 및 설치 후 접근성 검사 통과.
- 1배속, 재공급 0.25초, 프레임당 상한 8, 워밍업 2초, 피로 회복 켬으로 100초 측정.
  최초 56개 공급 후 16개 도착·회수·재공급. 100개 측정 행에서 Task 배정 8명, 회복 필요 0명.
  작업 유형은 실제 `CapsuleRelocationTask`로 확인했다.
- 시간 종료 시 신규 공급이 자동 중지됐으며 남은 운반의 도착·회수는 이후에도 진행됐다.
  검증 중 Console 오류 0건. 전체 잔여 운반 완료까지 기다리지는 않고 Play를 종료했다.
- CSV: `Temp/cargo-load-test-smoke.csv` (임시 검증 결과).
  이 결과는 기능 동작 확인이며 수백·수천 명의 처리 한계 측정 결과는 아니다.
